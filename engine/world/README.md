# @stratamu/engine-world

The engine's **authoritative game state**: what the `Runtime` executes against, as distinct from `Runtime`'s own bookkeeping (tasks, clocks, timelines, queues), which has no opinion about game state at all. See the architecture document's `Engine` sketch (`Runtime`, `WorldState`, `Sessions`, `Authority`, `Adapter`).

**Status:** prototype, deliberately minimal. Private and unpublished.

## What exists

- `WorldState`: the authoritative entities in the world — what exists, each thing's identity, and where it is. `add`, `get`, `has`, `remove`, `entities()`, `size`, `locate`, `locationOf`, `occupants`. Location was the first thing an actual feature (movement) revealed was needed; it stays the only relationship `WorldState` knows about — and it *is* the containment primitive, not a placeholder waiting for one: an entity located at another entity is contained by it, whether that other entity is a room, a character, or (once something needs it) a container. `occupants(id)` doesn't add a second relationship — it's a query over that same location data, not a maintained index, revealed by the next feature (multi-recipient messaging) needing "who is here" rather than "where is this one entity". It returns `EntityId`s (`IterableIterator<EntityId>`), not `Entity` records, to match `locationOf`/`locate`'s own model and stay a plain fact rather than a lookup — and takes no options: everyone at a location comes back, including whoever asked, so a filter like "exclude the speaker" stays the caller's concern, not `WorldState`'s. `WorldState` doesn't even know that a location is a "room": `locate(id, at)` just records that `at` is another entity's id, and `locationOf`/`occupants` hand that back unchanged. AberMUD's GET and DROP (`adapter-abermud`'s `commands/get.ts`/`drop.ts`) confirmed this holds for "held by a character" too, with no new method: picking an object up is simply `locate`ing it at the character instead of the room. A game-level name such as "inventory" or "room contents" is just `occupants` of a particular entity -- ownership and other relationships beyond location remain undesigned, discovered from what an adapter actually needs, same as before.
- `EngineState`: `{ readonly world: WorldState; readonly sessions?: Sessions }`. What the engine executes against. `world` is required; `sessions` (`@stratamu/engine-sessions`, see its README) is optional, so every earlier proof that builds an `EngineState` with only `world` keeps compiling unchanged — session lifecycle is a capability a `Runtime` can have, not one this interface now requires. `Authority`, named alongside both in the architecture document's `Engine` sketch, is still not here because it does not exist yet. This grows by adding fields as those are built, not by reserving space for them now.

`Entity` and `EntityType` live in [`@stratamu/entity`](../../libs/entity), not here: this package owns the authoritative *container*, not the shape of what it contains.

## How a handler reaches it

`Runtime` accepts an `EngineState` at construction (`RuntimeOptions.engineState`, optional — a `Runtime` has no opinion about game state, so it works without one) and threads its `world` through to `TaskContext.world`, unread and uninterpreted, for both a scheduler-run task and an inline one. See `@stratamu/engine-core`'s "vertical slice" test for the whole path proven end to end: `Input -> Work -> Task -> Runtime -> TaskHandler -> EngineState -> WorldState -> Output`.

`WorldState` is not the authority system. `world.add(entity)`/`world.remove(id)`/`world.locate(id, at)` are still data-integrity operations rather than game rules: `add` rejects duplicate ids, `locate` requires both entities to exist, and `remove` refuses to delete an entity that another entity currently references as its location so it cannot leave a dangling reference. *Whether* a move or deletion should be allowed by game rules (an exit exists, the entity can act, a room may be destroyed while occupied, anything else) is entirely the caller's concern, decided before these operations are called — see `@stratamu/engine-core`'s "world movement" proof, where movement permission lives in the handler, not here. That is fine for now: this is an internal authoritative data structure, not a public game API. Whatever eventually decides *whether* a mutation is allowed in general (`Authority`, in the architecture document's `Engine` sketch) sits between a handler and `WorldState`, not inside it — that boundary has no design yet, and isn't being retrofitted in speculatively.

## Not yet

- Relationships other than location -- ownership, attributes, anything not expressible as "located at another entity". Not designed wholesale — discovered from what an adapter actually needs. The old giant `BaseEntity` (id, type, name, description, location, owner, flags, attributes, timestamps...) is exactly what this is avoiding.
- Nested containment beyond one level (an item in a chest in a room). `locate` already supports it structurally -- nothing stops locating an entity at an entity that is itself located somewhere -- but nothing has asked for it yet, and with it comes a check this package does not make: cycle prevention (an entity cannot become located, even transitively, at something it already contains). A single level, which is all GET/DROP need, cannot produce a cycle, so there is no test for one here.
- `Authority` on `EngineState`. `Sessions` is implemented and remains optional on `EngineState`; `Authority` has no design yet: nothing stops a handler from calling `world.remove(...)` directly, bypassing whatever game rules should apply before the data-integrity checks.
- Persistence. `WorldState` is in-memory only.

## Depends on

`@stratamu/engine-sessions` (only for `EngineState.sessions`'s type — `WorldState` itself has no session concept), `@stratamu/entity`, `@stratamu/primitives`.
