# Repo notes for Claude

This repository is a Node.js Turborepo starter built as a pnpm workspace. It is intended to provide the foundation for Node-based applications and packages rather than a Next.js application.

The repository should remain deliberately generic until project-specific packages are introduced. Do not reintroduce Next.js, React, or browser-specific assumptions into the starter unless the project explicitly requires them.

## Git workflow

- `main` — stable, released state only. Nothing lands on `main` directly.
- `develop` — integration branch and the repository's **default branch**. Ongoing development happens here.
- Feature branches start from `develop` and merge back into `develop`.
- `develop` merges into `main` only as part of a release.
- Pull requests should be used for merges into both `develop` and `main`.
- Do not commit directly to `main`.
- Do not merge feature branches directly into `main`.

### Every `develop` → `main` merge is a release

`main` only moves at a release. Any `develop` → `main` merge that contains a change must therefore follow the release process.

Before the release PR is merged:

1. **Changesets must be present.**
   - Every user-facing package change must have an appropriate `.changeset/*.md` entry.
   - Use the correct semver bump for each affected published package.
   - If the release contains no user-facing package changes, use an empty changeset so the release intent is explicit.
   - Do not silently bypass Changesets because a change appears small.

2. **Versioning must be applied from the changesets.**
   - Run `changeset version` before the release is merged.
   - Commit the resulting package version and changelog changes as part of the release.
   - Do not manually invent package versions when Changesets should determine them.

3. **The release must be tagged.**
   - After the release merge reaches `main`, create the appropriate `v<version>` tag.
   - Push the tag to the remote repository.

4. **Release notes must be published.**
   - Create the corresponding GitHub release for the version tag.
   - Use the generated changelog information as the basis for the release notes.

A `develop` → `main` PR that contains release-worthy changes but has no appropriate changeset or versioning is not ready to merge.

### Changesets

Changesets live in:

```text
.changeset/
```

When adding a change:

```bash
pnpm changeset
```

When preparing a release:

```bash
pnpm changeset version
pnpm install
```

Commit the resulting version/changelog changes before merging the release PR.

Do not remove or modify an existing changeset merely to make CI pass without understanding what release information it represents.

If a package is private and unpublished, do not assign it a meaningless public version bump merely because it changed. The Changesets configuration and package visibility determine what should actually be versioned.

## Commits

Follow the repository's commit convention:

```text
<type>(<scope>): <subject>
```

Use imperative language and keep the subject concise, preferably within 72 characters.

Examples:

```text
feat(engine): add entity registry
fix(storage): handle missing world file
refactor(types): simplify entity definitions
chore(deps): update TypeScript
```

### Absolutely no commit attribution trailers

**Never add `Co-Authored-By:` to a commit message.**

This prohibition is absolute.

Do not add:

```text
Co-Authored-By:
```

or any variation of it.

Also do not add:

- `Generated with ...`
- `Generated by ...`
- `Created with ...`
- AI/tool attribution lines
- assistant attribution trailers
- equivalent generated-by metadata in commit messages

The Git history must contain **no `Co-Authored-By` or equivalent tool-attribution lines**.

When creating or amending commits, inspect the final commit message if necessary to ensure these lines have not been introduced automatically by a tool.

## Node.js

This is a Node.js project.

Do not introduce framework-specific assumptions from the standard Turborepo Next.js starter.

The repository should remain:

- Node-first
- ESM-first
- TypeScript-based
- pnpm-based
- Turborepo-managed

Applications and packages should use the shared TypeScript configuration rather than maintaining unrelated compiler settings.

## TypeScript

TypeScript is currently pinned to the `6.x` major.

Do not upgrade to TypeScript 7 or another major version without explicitly verifying compatibility across the repository.

When changing the TypeScript version:

- update the pnpm catalog;
- verify the shared TypeScript configuration;
- run type checking across the workspace;
- verify the build tooling;
- verify ESLint/TypeScript integration;
- update any relevant dependency constraints.

Do not allow a grouped dependency update to silently move TypeScript to a new major.

## Package management

Use **pnpm** for dependency management.

Do not use npm or Yarn to modify the workspace lockfile.

Workspace dependencies should use the workspace protocol where appropriate:

```json
"@stratamu/package": "workspace:*"
```

Shared dependency versions should remain in the pnpm workspace catalog where the repository already centralizes them.

After dependency changes, keep `pnpm-lock.yaml` synchronized with the manifests.

## Turborepo

Turborepo is responsible for orchestrating workspace tasks.

Root commands should delegate to Turbo rather than hard-coding knowledge of individual applications.

Typical commands include:

```bash
pnpm dev
pnpm build
pnpm lint
pnpm typecheck
pnpm test
```

Workspace packages should expose the corresponding scripts where those tasks apply.

Build artifacts should use Node-oriented output such as:

```text
dist/
```

Do not introduce `.next/` or other Next.js-specific build conventions.

## Workspace structure

The repository uses:

```text
apps/*
packages/*
```

Applications belong under `apps/`.

Reusable libraries and tooling packages belong under `packages/`.

The starter should not acquire packages merely to mirror the standard Turborepo template. Add a package when there is a clear architectural responsibility for it.

The intended direction for the Node project may eventually resemble:

```text
apps/
  server/

packages/
  engine/
  networking/
  presentation/
  storage/
  types/
```

Do not create these packages speculatively. Introduce them when their responsibilities are established.

## Shared configuration

Shared TypeScript configuration belongs in:

```text
packages/typescript-config/
```

Shared ESLint configuration belongs in:

```text
packages/eslint-config/
```

The Node starter should provide Node-oriented configurations rather than Next.js-specific configurations.

Do not add React, Next.js, DOM, or browser configuration to the shared base merely because a future application might need it. Platform-specific requirements belong in platform-specific configurations.

## Formatting and editor configuration

`.editorconfig` is part of the repository foundation and should be retained.

Formatting and editor conventions should remain consistent across:

- source files;
- configuration files;
- JSON;
- YAML;
- TypeScript;
- JavaScript;
- shell scripts.

Do not remove `.editorconfig` as part of framework or application cleanup.

Use the repository's configured formatter rather than introducing competing formatting conventions.

## Testing

Testing infrastructure should be introduced at the workspace level when the first package requiring tests is added.

Do not add a testing framework merely for the sake of having one in the starter.

When testing is introduced:

- provide shared configuration where appropriate;
- keep package-specific tests with the package they exercise;
- expose a consistent `test` script;
- integrate the test task with Turborepo.

## Dependencies

Prefer dependencies already established by the repository.

Before introducing a new dependency:

1. determine whether the functionality can reasonably be provided by the platform or existing tooling;
2. check whether another workspace package already provides the required capability;
3. consider whether the dependency belongs at the root, in an application, or in a reusable package;
4. keep dependency ownership as narrow as practical.

Do not add framework dependencies simply because they are common in Turborepo examples.

## Repository cleanup

When converting or maintaining the starter, remove stale framework-specific configuration rather than leaving dead configuration behind.

In particular, do not leave references to:

- Next.js;
- `.next/`;
- Next ESLint configuration;
- React-only TypeScript configurations;
- unused workspace directories;
- nonexistent configuration packages;
- obsolete scripts.

A clean repository is preferable to preserving configuration merely because it existed in the original template.

## Changes should be deliberate

This repository is intended to be a foundation for subsequent architecture work.

Prefer small, coherent changes over broad speculative restructuring.

When changing repository infrastructure:

1. understand the existing configuration;
2. make the smallest change that establishes the intended architecture;
3. run the affected validation commands;
4. verify the workspace and Turbo dependency graph;
5. document an architectural decision when the choice has long-term consequences.

Do not copy the structure of another repository wholesale. Use prior projects as references where useful, but adapt decisions to this repository's actual requirements.

## Before completing work

Before considering a change complete, verify as appropriate:

```bash
pnpm install
pnpm build
pnpm lint
pnpm typecheck
pnpm test
```

Also verify that:

- the working tree contains only intended changes;
- no stale framework references remain;
- workspace dependencies resolve correctly;
- Turbo recognizes the affected packages;
- generated files are not accidentally committed;
- commit messages contain **no `Co-Authored-By:` or equivalent attribution lines**.

For release work, additionally verify:

- the appropriate changesets exist;
- package versions are correct;
- changelogs are updated;
- the release is being made from `develop` into `main`;
- the release tag matches the resulting version.
